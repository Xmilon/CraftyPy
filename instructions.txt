=====================================================================
1. GOAL
=====================================================================

An in-game "computer" block that opens an IDE where the player writes
PYTHON scripts to add content to Minecraft: blocks, items, entities,
effects, recipes, loot tables, tags, sounds, interactions and events.
Everything is organized in PROJECTS stored in the game instance folder,
and projects can be loaded, reloaded and unloaded without editing the
mod itself. The experience should resemble MCreator's asset handling,
but code-first.


=====================================================================
2. HARD TECHNICAL CONSTRAINTS (design around these, don't ignore them)
=====================================================================

2.1 REGISTRIES ARE FROZEN AFTER MOD LOADING IN 1.21.1
Blocks, items, entities and block entities cannot be truly registered at
runtime. Implement a hybrid:

  - SLOT-POOL SYSTEM (default): pre-register N generic slot objects at
    startup (configurable, e.g. 256 blocks, 256 items, 64 entities,
    32 mob effects, 32 sound events, 16 block entities). A project
    "claims" slots, and a data definition (JSON in the project) drives
    their behavior and appearance. Override the relevant methods
    (getDestroyProgress, getExplosionResistance, use, getLightEmission
    via a blockstate property, appendHoverText, etc.) to read from the
    definition at runtime. Display names, models, textures and sounds
    come from a DYNAMIC RESOURCE PACK.

  - RESTART MODE (optional, documented): if a project needs more than
    the pool allows, or needs a truly separate registry entry, mark it
    "requires restart" and register it in the next startup phase.

  - Clearly document which things are hot-reloadable (recipes, loot
    tables, tags, advancements, lang, textures, models, sounds,
    behavior scripts) and which are not.

2.2 DYNAMIC PACKS
Implement an in-memory/on-disk PackResources + RepositorySource for both
a resource pack (client) and data pack (server) generated from the
active projects. Hook with AddPackFindersEvent. Loading a project must
trigger a resource reload (client) and a datapack reload (equivalent to
/reload) automatically. Sync resources to clients in multiplayer.

2.3 PYTHON RUNTIME
Use the NEWEST STABLE CPython (3.13+, or 3.14 if stable), bundled or
auto-downloaded on first run into the instance's pyforge/runtime/ folder
(per OS: Windows/Linux/macOS, with checksum verification). Run it as a
SANDBOXED EXTERNAL SUBPROCESS (one per loaded project or one shared
worker) communicating with Java via a JSON-RPC protocol over
stdin/stdout or a local socket. Do NOT use Jython (Python 2.7 only). If
you evaluate GraalPy as an alternative, document its Python version
limits and why you chose or rejected it. Provide a fallback message in
the IDE if Python is missing or fails.

2.4 PYTHON IS DECLARATIVE-FIRST
Scripts mainly DECLARE content at load time (@block(...), Block(...))
and register EVENT HANDLERS (callbacks that run on the Python worker and
call back into Java through a whitelisted API). Handle latency:
callbacks run async with a per-call timeout (default 50 ms budget on the
server tick, configurable). Anything exceeding it is cancelled and
logged. Support "pure data" properties so common behavior runs entirely
in Java with no Python round-trip.

2.5 SIDES
Server-authoritative. The IDE UI is client-side; project files live on
the server (singleplayer integrated server = same instance folder). On
dedicated servers, upload/edit goes through packets with size limits and
permission checks.

2.6 SECURITY
Python code is effectively arbitrary code execution. Mitigate:
  (a) only ops (permission level configurable, default 2) or the
      singleplayer owner can open/edit/load projects,
  (b) config option to completely disable the mod's scripting,
  (c) the subprocess runs with the project folder as its working
      directory, an import allowlist (stdlib subset: math, random, json,
      re, dataclasses, typing, enum, time, datetime, collections,
      itertools, functools), blocking os, subprocess, socket, ctypes,
      importlib tricks, open() outside the project folder, and
      __import__ abuse. Document honestly that this is BEST-EFFORT AND
      NOT A HARD SANDBOX, and list OS-level hardening options (Windows
      job objects, Linux seccomp/namespaces if feasible).
  (d) A warning screen when loading a project from an unknown
      source/zip.

2.7 COMPATIBILITY
Must not crash if other mods are present. Asset pools must include
vanilla and all loaded mods.

3. PROJECT AND FILE STRUCTURE (inside the game instance)
=====================================================================

<instance>/pyforge/
  runtime/                 # bundled/downloaded Python
  logs/                    # per-project + global logs
  projects/
    <project_id>/
      project.json         # id, name, version, author, description,
                           # mc_version, api_version, requires_restart
                           # flag, slot usage
      code/                # .py files (main.py + modules)
      assets/
        textures/ models/ sounds/ lang/ animations/ other/
      data/                # generated or hand-written datapack JSON
                           # (recipes, loot tables, tags, advancements)
      build/               # generated packs (disposable, regenerable)
  exports/                 # .pyforge zip exports
  imports/                 # drop zips here

All project files must be plain files so users can also edit them in an
external editor, and the mod must detect external changes (file watcher)
and offer to reload.

4. PYTHON API (v1, keep it simple but extensible)
=====================================================================

Provide a typed Python module "pyforge" (with .pyi stubs so
autocomplete works in the IDE) such as:

    from pyforge import *

    @block("ruby_block")
    class RubyBlock:
        name = "Ruby Block"
        texture = tex("minecraft:block/dirt")   # or tex("project:ruby")
        hardness = 2.0
        resistance = 6.0
        light = 5
        sound = snd("minecraft:block.amethyst_block.chime")
        tool = "pickaxe"; needs_tool = True
        drops = loot_self()                     # or custom loot table

        def on_right_click(self, ctx):
            ctx.player.send_message("Hello!")
            ctx.world.play_sound(
                snd("minecraft:entity.experience_orb.pickup"), ctx.pos)

    @item("ruby") ...
    @entity("slime_pet") ...    # based on a base type like "mob_passive"
                                # / "mob_hostile", simple stats and
                                # textures
    @effect("glowy") ...
    recipe_shaped(...), recipe_shapeless(...), recipe_smelting(...)
    loot_table(...), tag(...),
    @on("player_join") / @on("block_break") / @on("tick", every=20) ...

SCOPE FOR v1: blocks, items, simple entities (reskinned base AI types
with configurable stats, no custom Java AI), mob effects, recipes, loot
tables, tags, sounds, lang, simple events, commands (via a brigadier
wrapper), world/player/inventory helpers.

Document the full list of WHAT IS POSSIBLE, WHAT IS LIMITED AND WHAT IS
NOT POSSIBLE (e.g. no custom dimensions, no custom GUIs/menus in v1, no
custom rendering code, no arbitrary NMS/Java access, no new complex
entity AI, no new block entity with custom inventory in v1 unless
implemented).

=====================================================================
7. LOAD / RELOAD / UNLOAD LIFECYCLE
=====================================================================

1. VALIDATE (static + schema + registry/slot checks + asset existence).

2. BUILD: generate resource pack + datapack into build/, allocate slots
   (persist the slot mapping in the world data so blocks placed in a
   world keep working across reloads and restarts, keyed by project ID +
   content ID).

3. LOAD: start/reuse the Python worker, run the scripts to collect
   declarations, apply definitions to slots, enable the packs, trigger
   resource + data reload, sync to clients.

4. UNLOAD: remove the packs, release the behavior, and make slot objects
   revert to a harmless "unloaded" state (placeholder texture, no
   behavior, name shows "Unloaded: project:id") so placed blocks and
   items in worlds do NOT vanish or corrupt saves. Re-loading the
   project restores them. Provide a "purge project content from world"
   tool as an optional advanced and clearly warned action.

5. HOT RELOAD ON SAVE (optional toggle) with debounce. Handle errors by
   keeping the last known-good version running ("rollback on failure").

6. EDGE CASES to handle:
   - two projects defining the same ID (namespace by project ID by
     default)
   - a project deleted while loaded
   - Python worker crash (auto-restart with backoff and a crash counter)
   - world switch/disconnect (unload client-side packs)
   - multiplayer join with different loaded projects (sync + version
     check)
   - removed slots
   - slot pool exhaustion (clear error and a config hint)
   - case-sensitivity on Windows/Linux
   - very large assets
   - invalid UTF-8
   - line endings
   - project files modified externally

=====================================================================
NOTES (not part of the prompt)
=====================================================================

- THE SLOT-POOL APPROACH IS THE KEY DECISION. It's what lets you hit
  "load a project and /reload adds blocks" without a restart. The
  trade-off is a fixed maximum (configurable) and slightly more complex
  block behavior code.

- PYTHON IN-PROCESS VS EXTERNAL: An external subprocess is specified
  because it's the only way to get a current CPython. If you'd rather
  accept an older language level for simplicity, GraalPy is the in-JVM
  alternative, which you could mention to the AI.

- This is a very large project. Expect to run it milestone by milestone
  across many sessions rather than in one go. Pasting REPORT.md back
  into the AI at the start of each new session is a good way to keep it
  on track.

- A shorter "milestone 1 only" version of the prompt can be written to
  get started faster.
