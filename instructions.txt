3. MODULES (build, store, enable, plugin-style)
=====================================================================

3.1 What a module is
  A "module" is a project built into ONE readable file: a standard ZIP
  with the extension .cpm (CraftPy Module). No obfuscation, no custom
  binary format: anyone can open it with a normal zip tool. Layout:

    module.json            manifest (see 3.2)
    code/                  .py sources (plain text, included always)
    assets/<ns>/...        textures, models, sounds, lang, fonts
    data/<ns>/...          recipes, loot tables, tags, advancements,
                           worldgen JSON (version-neutral source, see 5)
    docs/                  optional markdown shown in the Modules screen
    LICENSE, README.md     optional
    checksums.json         sha256 of every file (+ manifest hash)

  Building is deterministic (sorted entries, fixed timestamps) so the
  same project always produces the same hash.

3.2 module.json (schema version 1; validate it with a JSON schema)
  {
    "schema": 1,
    "id": "ruby_pack",                // [a-z][a-z0-9_]{1,31}
    "name": "Ruby Pack",
    "version": "1.2.0",               // semver
    "author": "Xmilon",
    "description": "...",
    "api_version": "1.0",             // CraftPy Python API level it was written for
    "mc_versions": ["1.21.1"],        // versions it is declared to work on
    "side": "server",                 // server | client | both
    "entry": ["code/main.py"],
    "dependencies": [ {"id": "core_lib", "version": ">=1.0 <2.0", "optional": false} ],
    "conflicts": [ "old_ruby_pack" ],
    "capabilities": ["ui", "commands", "worldgen"],   // features it needs (checked at load)
    "permissions": ["storage", "network_message"],    // dangerous things it asks for (user must approve)
    "startup": false,                 // a hint only; real startup = the startup/ folder
    "requires_restart": false,
    "slots": { "blocks": 3, "items": 5, "entities": 1, "effects": 0 }
  }

3.3 Folder layout (inside the game instance, next to the existing
    pyforge/ data):

    <instance>/pyforge/modules/
        startup/        MANDATORY modules: everything in here loads
                        automatically at game launch (client resources at
                        client startup, server data when the server
                        starts), before modules.json modules, in
                        dependency order. They cannot be disabled from
                        the UI (shown with a lock icon); remove the file
                        to remove the module.
        modules.json    the config file: which OTHER modules are
                        enabled, their order and per-module settings.
        library/        every saved/built/imported module (.cpm). This is
                        the pool modules.json refers to. Dev projects can
                        also appear here as unpacked folders.

    modules.json (schema 1), written ATOMICALLY (temp file + rename),
    watched for external edits (reload on change, with a debounce):
    {
      "schema": 1,
      "enabled": [
        { "id": "ruby_pack", "version": "1.2.0", "file": "library/ruby_pack-1.2.0.cpm",
          "order": 10, "settings": { "difficulty": "hard" } }
      ],
      "disabled": ["old_pack"],
      "approved_permissions": { "ruby_pack": ["storage"] },
      "safe_mode": false
    }

3.4 Plugin-style behaviour (no package swapping)
  Modules are SERVER-AUTHORITATIVE, like datapacks/plugins: players do
  NOT install or exchange modules. The server owns the module files; on
  join it sends the client a manifest (id, version, hash) and any
  resources the client is missing (compressed chunks over NeoForge
  networking, cached under pyforge/cache/<hash>/, bandwidth-capped,
  resumable). Clients only need the CraftPy mod itself (the slot pool is
  registered by the mod). If a client has an older mod/API level, refuse
  the join with a clear message. In singleplayer the integrated server
  does the same without copying.
  Client-only modules (side="client") are allowed but restricted
  (no server-side effects) and never auto-downloaded.

3.5 Lifecycle for a module
  validate -> resolve dependencies -> allocate slots (persisted mapping)
  -> run Python -> build resource+data packs -> apply on the correct
  thread -> resource/data reload -> sync to clients.
  Disable/unload: remove packs, release behaviour, slot objects revert
  to the harmless "unloaded" state (placeholder, no behaviour, name
  "Unloaded: module:id") so worlds are never corrupted. Re-enabling
  restores them. Handle: dependency cycles, missing dependencies,
  version conflicts, two modules defining the same id (always namespaced
  by module id), a module deleted while enabled, crash loops (after N
  crashes auto-disable the module and offer SAFE MODE), startup module
  failing (game still starts, error shown), requires_restart modules.

3.6 Build from the IDE and commands
  - IDE: Run > Build Module (Ctrl+Shift+B) with a dialog: version bump,
    changelog text, include sources (default yes), validate first.
    Output goes to library/. The Problems panel shows build errors.
  - Command line / Gradle task: ./gradlew buildModule -Pproject=<id>
    (headless, for CI), and /craftpy module build <project>.
  - Import: file dialog (LWJGL TinyFD) + drag-and-drop of .cpm onto the
    Modules screen; verify checksums, show manifest + requested
    permissions and a warning for unknown sources BEFORE enabling.
  - Export: any library module can be exported/copied.

3.7 The Modules screen (SEPARATE screen, not inside the IDE)
  Opened by: /craftpy module (opens the screen for admins), a keybind,
  the IDE menu (Modules > Manage...), and the computer block.
  Contents:
    - Left: searchable/filterable list of startup + library modules with
      status badges (Enabled, Disabled, Loaded, Error, Needs restart,
      Locked/startup, Update available (newer version in library)).
    - Per-row toggle (enable/disable) for non-startup modules. Toggling
      updates modules.json immediately and shows a pending-changes bar:
      [Apply] [Revert]. Apply runs the lifecycle for the changes only.
    - Right: details panel (manifest, description/docs markdown,
      dependencies with their state, conflicts, requested permissions
      with approve/revoke, size, hash, content counts, slot usage, load
      time, per-module log tail, per-module settings generated from the
      module's declared config schema).
    - Load order control (up/down or drag), dependency auto-ordering,
      "enable with dependencies" and "disable dependents" prompts.
    - Buttons: Build from project, Import, Export, Delete (confirm),
      Open folder, Reload module, Reload all, Safe mode toggle.
    - Works on dedicated servers for admins through packets with
      permission checks; the screen shows the SERVER's modules.
  Everything here must use the ui-toolkit and the active theme.

4. THE PYTHON API: ONE SYNTAX, MANY GAME VERSIONS
=====================================================================

GOAL: a module written once keeps working across Minecraft versions, so
end users can keep using old code. Be honest about the limit: the Java
mod itself is built per Minecraft version/loader (today NeoForge 1.21.1);
what is portable is the PYTHON code and the DATA it declares.

4.1 Principles
  - Scripts NEVER import or name anything version-specific (no
    net.minecraft class names, no raw NBT/component layouts, no JSON
    formats of a given version). They use the CraftPy API only.
  - The API is versioned with semver (api_version). A module declares the
    api_version it was written for; the runtime executes it with THAT
    version's semantics (compat layer) as long as it is within the
    supported window. Breaking changes only on major versions; old
    behaviour stays available through compat shims for at least two
    majors, with deprecation warnings in the Problems panel and the
    console (never silent breakage).
  - Per-version adapters in Java translate neutral definitions into what
    each Minecraft version needs (recipe/loot/advancement JSON formats,
    item components vs NBT, registry differences, event names, rendering
    differences). Declarative content (blocks, items, recipes, loot,
    tags, effects, entities) is ALWAYS translated by the adapter. A
    clearly marked escape hatch raw_json(...) exists and is flagged
    "version-specific" by the linter.
  - Capability flags: features that do not exist everywhere are queried,
    not assumed: if cp.has("worldgen.biome_modifiers"): ... and the
    manifest "capabilities" list makes unsupported modules fail EARLY
    with a clear message instead of crashing at runtime.
  - Decorators @since("1.0"), @deprecated("1.4", use="...") in the API
    description, surfaced in autocomplete/docs/linter.
  - A migration assistant ("Upgrade module to API 2.0") that applies
    safe automatic rewrites (codemods) and lists manual changes.
  - Test matrix: an "old modules" corpus under tests/legacy/ (modules
    written for api 1.0) that must keep passing in CI against every new
    API version.

4.2 Coverage: convert the NeoForge/Minecraft surface into Python
  Produce docs/API_COVERAGE.md (generated) listing for every area:
  Implemented / Partial / Not possible (and why) / Planned. Implement in
  tiers; finish Tier 1 and Tier 2, start Tier 3:

  TIER 1 (declarative content - must be complete)
    blocks (properties, block states with typed properties, shapes,
      light, sounds, tool/needs_tool, friction, random ticks, redstone
      power in/out, waterlogging, drops, creative-tab membership,
      interactions: right/left click, step on, neighbor change, placed,
      broken, entity inside, projectile hit), block entities with
      persistent data (no custom rendering)
    items (stack size, durability, tools, armor, weapons, food and
      effects, fuel, use actions, cooldowns, components/data, attribute
      modifiers, enchantability, tooltips, interactions: use, use on
      block, use on entity, inventory tick)
    entities (base types + attributes + data-driven behaviour presets,
      spawn rules, drops, sounds, textures/models from the resource
      pack, riding, taming-lite), mob effects, potions + brewing recipes,
      enchantments (data-driven), damage types, attributes, game rules
    recipes (every vanilla recipe type: shaped, shapeless, smelting,
      blasting, smoking, campfire, stonecutting, smithing, plus custom
      "transmute"-style helpers), loot tables (all pools/conditions/
      functions), tags (all registries), advancements, lang/translations,
      sounds.json, particles, fonts
  TIER 2 (logic)
    events: map EVERY commonly used NeoForge event to a stable Python
      event name with a typed context object (player join/leave/respawn/
      death/chat/command, block break/place/interact, entity spawn/
      damage/death/tame, item use/craft/smelt/pickup/drop/toss, world/
      level tick/load/save, server start/stop/tick, container open/
      close, explosion, projectile, effect added/removed, fluid/redstone
      where exposed). Cancellable events expose .cancel(). Ordering and
      priorities available (@on("block_break", priority="high")).
    world/player/inventory helpers (get/set block, blocks in area,
      raycast, entities in box, spawn/kill, teleport, effects, attributes,
      inventory/ender chest access, XP, hunger, gamemode, advancements,
      scoreboards, teams, boss bars, titles/action bar, particles,
      sounds, weather/time, game rules, structure placement)
    scheduler (run_later, run_every, run_next_tick; cancellable handles)
    per-module persistent storage (key-value; per world, per player,
      per chunk-lite) with versioned migration hooks (on_upgrade)
    typed per-module config (schema -> auto settings UI)
    commands (Brigadier wrapper, typed arguments, suggestions,
      permissions, sub-commands)
    networking between module server code and its client UI (see 5)
  TIER 3 (advanced / stretch, document limits honestly)
    worldgen through datapack features and NeoForge biome modifiers
      (ores, trees, structures-lite), dimensions via datapack, fluids,
      simple custom GUIs with real item slots (container menus),
      HUD overlays, key mappings (client modules), capabilities-like
      item/fluid handlers, advancements triggers, loot modifiers
  EXPLICITLY NOT POSSIBLE / OUT OF SCOPE (state it in the docs table):
      arbitrary Java access, custom rendering code/shaders, new complex

5. WINDOWS INSIDE MINECRAFT (desktop-app style, written in Python)
=====================================================================

Goal: with Python you can build "desktop applications" that run inside
Minecraft: windows with buttons, text fields, lists, tabs, dialogs, etc.

5.1 Model (decide and document; recommended):
  - Python (server worker) DESCRIBES the UI as a widget tree and handles
    events. The Java client RENDERS it with the ui-toolkit and sends
    user events back. The client never executes module code. The server
    sends tree diffs (not full trees every frame), with size, rate and
    depth limits. Purely client-side modules (side="client") may run a
    separate restricted client worker.
  - The same ui-toolkit renders the IDE and the Modules screen, so every
    window gets the active theme, scaling and keybinds for free.

5.2 Python API sketch (keep it close to Tkinter/Qt so it feels familiar):

    from pyforge.ui import window, Window, VBox, HBox, Label, Button, TextInput, Slider

    @window("counter", title="Counter", size=(220, 140), resizable=True)
    class Counter(Window):
        def build(self, ctx):
            self.count = self.state(0)                  # observable state
            self.root = VBox(padding=6, gap=4, children=[
                Label(bind=lambda: f"Clicks: {self.count.value}"),
                Button("Click me", on_click=self.bump),
            ])
        def bump(self, event):
            self.count.value += 1

    # open it: from code, from a command, from a block/item click, from a keybind
    ui.open(player, "counter")
    # /craftpy window open ruby_pack:counter [player]

5.3 Widgets and features
  Window (title bar, close/minimize/maximize, drag, resize, z-order,
  focus, modal and non-modal, multiple windows per player, optional
  taskbar), Frame/Panel, VBox/HBox/Grid/Anchor/Flex layouts, Label,
  Button, IconButton, TextInput, TextArea, PasswordInput-lite, Checkbox,
  RadioGroup, Switch, Slider, Spinner, Dropdown/ComboBox, ListView,
  TreeView, Table (sortable columns), TabView, ScrollView, ProgressBar,
  Image (project textures), ItemIcon/BlockIcon, EntityPreview (stretch),
  Tooltip, MenuBar, ContextMenu, Toast/Notification, Dialogs (message,
  confirm, input, color picker, asset/file picker limited to the
  module's assets), ItemSlot grid (REAL server-side container menu so
  items can be moved safely), HUD overlays (non-interactive, anchored),
  world-space screens on a block entity (like the computer block), simple
  animations/transitions, drag and drop between widgets, keyboard focus
  and navigation, accessibility labels.
  Styling: themes + per-widget style classes (like CSS classes), no
  hard-coded colors in module code unless explicitly overridden.
  State: observable values with bindings; batched updates per tick.

5.4 Limits to document: latency (round-trip to the server), bandwidth
  budget per player, max widgets per window, update rate, text input
  goes through the server (IME/clipboard handled client-side and sent as
  text), no custom rendering code, textures only from the module's
  resource pack.

6. A REAL CONSOLE (not a textbox with canned commands)
=====================================================================

Replace the current console with a real interactive Python terminal.

6.1 Behaviour
  - A true REPL attached to a persistent interpreter (per project and per
    module; use code.InteractiveConsole semantics or equivalent) running
    in the Python worker: variables persist between lines, imports work
    (within the sandbox allowlist), functions and classes can be defined,
    the CraftPy API is pre-imported (cp, world, players, ui ...).
  - Multi-line input with continuation prompt ("..."), correct handling
    of blocks, auto-indent, paste of multi-line code.
  - stdout and stderr are streamed live and drawn in different colors;
    tracebacks are mapped to project file/line and are CLICKABLE (jump
    to the line in the editor); print() inside event handlers goes to
    the console of the owning module.
  - Prompt line with history (Up/Down, Ctrl+R reverse search, persisted
    across sessions in pyforge/history), Tab completion (identifiers,
    attributes, CraftPy API with docs, registry ids, file names), syntax
    highlighting while typing, bracket matching.
  - Ctrl+C interrupts the running statement (KeyboardInterrupt in the
    worker); Ctrl+L clears; Ctrl+D / exit() closes the session; input()
    works; long-running code never freezes the game.
  - Scrollback buffer (configurable size), text selection, copy/paste,
    search (Ctrl+F in the console), filter by level/module, word wrap
    toggle, timestamps toggle, save log to file.
  - Several consoles as tabs: "Python (project)", "Python (module X)",
    "Server log", "Game log". The server log tab is admin-only on
    dedicated servers.
  - Meta commands use a distinct prefix (":help", ":clear", ":run",
    ":modules", ":reload", ":debug") so they never collide with Python
    names. Minecraft commands are available through cp.command("...")
    and a ":mc <command>" shortcut.
6.2 Safety: REPL execution requires admin permission and the config
  switch scripting.console.enabled; every executed line is logged with
  the player name; a per-line timeout is OFF by default but an interrupt
  always works; the REPL runs with the same sandbox as modules unless the
  admin enables "unsafe console" in the server config.
6.3 Threading: input/output pipes are async; the render thread only
  copies from a thread-safe ring buffer; apply results to game state
  back on the main thread.

7. COMMANDS AND PERMISSIONS (cheat-class = admin only)
=====================================================================

Use Brigadier. Root literal: /craftpy. EVERY CraftPy command requires an
operator by default (permission level 2 minimum; dangerous ones 3-4),
works only when cheats are enabled in singleplayer, and permission levels
are configurable in the server config. Also register NeoForge
PermissionAPI nodes (craftpy.command.<name>) so permission mods can
override them. Provide full tab-completion and clear error messages.

  /craftpy ide [open|close] [player]        open/close the IDE for a player
                                              (no block needed; keybind too)
  /craftpy ide project <id>                 open the IDE on a project
  /craftpy module                            open the Modules screen
  /craftpy module list|info <id>
  /craftpy module enable|disable <id>        updates modules.json
  /craftpy module reload [<id>|all]
  /craftpy module build <project> [version]
  /craftpy module import <file>|export <id>
  /craftpy module unload <id>
  /craftpy module purge <id>                 remove its content from the
                                              world (level 4, confirmation)
  /craftpy module trust <id> <permission>    approve a dangerous permission
  /craftpy safemode [on|off]
  /craftpy project new|list|delete|run|stop <id>
  /craftpy give <targets> <project:content> <block|item> [count]
      Example: /craftpy give Dev project_bb:ruby block
      The content kind is part of the command so a block and an item
      with the same id never collide. Project content is NOT looked up in
      the item registry. Block vanilla commands (/give, /setblock, /fill,
      /clear, execute ... run give) from using pooled slot objects
      (cancel the command via NeoForge CommandEvent with a message that
      points to /craftpy give). Keep slot objects out of creative tabs
      and use neutral registry ids (craftpy:slot_17). Document the limit:
      vanilla tab-completion reads the registry and cannot be filtered
      without replacing the vanilla argument types.
  /craftpy setblock|fill|summon <project:content> ...   place/spawn project content
  /craftpy py <code>                         run one line of Python (level 3)
  /craftpy exec <module>:<file>              run a script file (level 3)
  /craftpy window open|close <module:window> [player]
  /craftpy storage get|set|clear <module> <key> [scope]
  /craftpy debug reload|unload|list|slots|dump <id>|profile|trace|worker restart|rpc
  /craftpy config get|set <key>              server config values
  /craftpy test run <module>                 run the module's tests

Modules can register their own commands through the Python API
(@command(...)). Their default permission is admin; a module may ask for
a lower level but the server config can cap it
(module_commands.max_player_level, default: none allowed for players).

Cheat-class gameplay helpers shipped by the mod itself (all admin only,
all implemented on top of the public API so they double as examples):
give/summon/setblock/fill of project content, heal/feed/god-lite via
effects and attributes, time/weather presets, clear-and-reset content in
an area, and a "creative content browser" screen (admin only) that lists
loaded project content to take from.

8. THE IDE - PROFESSIONAL, THEMED, KEYBOUND
=====================================================================

Rebuild the IDE UI on the ui-toolkit with a real design system.

8.1 Design system
  - Design tokens in JSON: colors (bg0-bg3, surface, border, text,
    text-muted, accent, success, warning, error, selection, focus ring,
    syntax colors), spacing scale (4px grid), radii, font sizes, icon
    size, animation durations. Every widget reads tokens, never raw
    colors.
  - Built-in themes: Dark (default), Light, High Contrast, Solarized
    Dark, Monokai-like, Dracula-like, Colorblind-safe. User themes are
    JSON files in pyforge/themes/*.json, hot-reloaded, with a live preview
    in Settings. Modules can ship themes too. Run an automated WCAG AA
    contrast check on built-in themes.
  - Fonts: Minecraft font OR a bundled monospace TrueType font (use
    Minecraft's ttf font provider; choose an OFL-licensed font such as
    JetBrains Mono, include the license), size 8-24, line height,
    optional ligatures.
  - Icon set: a pixel-art icon atlas for file types, toolbar actions,
    problem severities, run/debug states (original art, no copyrighted
    assets).
  - UI scale 50-300% independent of Minecraft's GUI scale, reduce-motion
    option, high-contrast option, narrator labels on interactive widgets.
  - Subtle animations (hover, panel open/close, toasts) that can be
    turned off.

8.2 Layout
  - Dockable, resizable panels with draggable splitters; layout saved
    and restored (pyforge/layouts/*.json); presets (Default, Focus,
    Debug). Tabs: closable (x button + middle click + Ctrl+W), reorder by
    drag, pinned tabs, preview (italic) tabs, overflow menu, split editor
    (horizontal/vertical), breadcrumbs, status bar with clickable items
    (Python version, API version, MC version, module state, theme, line/
    column, encoding, line endings).
  - Explorer: project tree with folders, file-type icons, and an ASSETS
    section listing the project's textures/sounds/models; clicking an
    asset opens a VIEWER tab (texture preview with zoom and pixel info,
    sound player with waveform + play/stop/loop/volume, model viewer) and
    right-click offers Copy ID, Copy tex("..."), Insert at cursor, Edit,
    Replace, Delete. Drag an asset into the code to insert a reference.
  - Welcome screen: recent projects, templates (block, item, mob, window
    app, command, HUD), docs links, news from the changelog.
  - Settings screen: searchable categories (Appearance, Editor, Keymap,
    Python, Modules, Debug, Security), backed by JSON, import/export.
  - Command palette (Ctrl+Shift+P): fuzzy search of every action with its
    shortcut. Quick open (Ctrl+P) for files/assets/symbols. Global
    search and replace (Ctrl+Shift+F) with regex, scope and preview.

8.3 Keybinds
  - A central action registry; every action has an id, label, default
    shortcut per keymap, and a context (editor, console, explorer,
    global). Rebindable in a Keymap editor with conflict detection, search
    by action or by pressed keys, reset per action/all, import/export.
  - Keymap presets: Default, IntelliJ-like, VS Code-like (Vim-lite as a
    stretch). Chords supported (Ctrl+K Ctrl+C). Stored in
    pyforge/keymaps/*.json.
  - Minecraft keybinds must never fire while typing; the IDE captures
    keys in text contexts. Shortcut hints appear in menus and tooltips.
  - Global shortcut to open the IDE without the block (configurable,
    admin only, default unbound) and one for the Modules screen.

8.4 Editor
  - Syntax highlighting (Python + JSON + markdown), line numbers, indent
    guides, code folding, bracket matching + colorization, current-line
    highlight, whitespace toggle, minimap (stretch), word wrap, sticky
    scroll (stretch).
  - Editing: undo/redo history, multi-cursor (Ctrl+click, Ctrl+D), column
    selection, move/duplicate/delete line, toggle comment, indent/
    unindent, smart auto-indent, auto-close brackets/quotes, surround
    selection, rename symbol (project-wide), format document (bundled
    formatter such as ruff/black run in the worker, optional), format on
    save.
  - Intelligence: diagnostics (Python compile + linter + CraftPy API
    validation) with inline squiggles, gutter markers, quick fixes
    (lightbulb), hover documentation from the API description, signature
    help with parameter hints, go to definition (Shift-click and F12),
    find usages, outline/structure view, snippets.
  - Completion (replaces the current popup; fixes P6): a suggestion
    popup that is recomputed from the live cursor on every change, so it
    can NEVER stay on screen after you type something unrelated;
    ranked results with icon, signature and a SHORT DESCRIPTION of the
    selected entry; Esc dismisses until the token changes; Tab accepts;
    Up/Down choose; Ctrl+Space forces. Context aware: inside a @block
    class it offers block fields (minus those already written), after "="
    it offers value helpers, inside @on("...") event names, after "ctx."
    members, inside quoted enumerated fields (tool, base) their values.
    SMART FILL ("fill in the block"): when a declaration line such as
    @block("ruby_block") is complete, show the generated class body as
    GHOST TEXT (grey preview in the editor) with the fields that block
    normally needs; Tab inserts it, any other typing dismisses it. Do
    this for block/item/entity/effect. Inserting it must be one undo
    step and must keep the cursor/undo history.
  - Assets inline: thumbnails/swatches in the gutter next to tex()/snd()/
    mdl(), hover preview, click opens the picker/viewer, missing assets
    flagged in Problems.
  - Local history: snapshot on every save, timeline + diff viewer (compare
    with last saved / last built / any snapshot). Auto-save and crash
    recovery. External-edit detection with reload prompt.
  - Run/Debug toolbar: Run, Stop, Reload, Validate, Build Module, with
    progress and cancel. Breakpoints and a variable inspector are a
    stretch goal (document the design if not done).

8.5 Performance targets for the UI: 60 fps on a 10,000-line file;
  virtualized lists/trees; cached text layout; no per-frame allocation
  in hot paths; hit-testing always uses the same geometry as rendering
  (see P3); redraw only what changed where practical.

9. SECURITY AND ROBUSTNESS (modules are code)
=====================================================================

  - Capabilities/permissions per module (storage, network_message, file
    access limited to the module folder, scheduler, commands, ui,
    worldgen...). Dangerous ones need explicit admin approval stored in
    modules.json ("approved_permissions"). A consent dialog shows what a
    module asks for BEFORE it is enabled the first time.
  - Sandbox (best-effort, say so): import allowlist, blocked os/
    subprocess/socket/ctypes/importlib tricks, open() only inside the
    module folder, resource limits (call time budget, memory cap where
    the OS allows, message rate, output size), watchdog that kills and
    restarts a stuck worker. Isolation level configurable: shared worker
    with per-module namespaces (default) or one process per module.
  - A crash/timeout in one module never takes down others. Crash loops
    auto-disable the module; SAFE MODE starts the game with all non-
    startup modules off (also via a launch flag or a file marker).
  - Optional integrity: sha256 pinning in modules.json, optional signing
    with a "trusted publishers" list (stretch).
  - All packets validated: sizes, rates, permission, project/module
    existence, path traversal checks on every file path.
  - Config switch to disable scripting completely.

11. THREADING AND PERFORMANCE
=====================================================================

  - The Minecraft main threads (server tick, client render) must never
    run: Python compile/validate, module build/zip, file IO, asset
    indexing, thumbnail/texture decoding, checksum, network chunk
    assembly, file watching or JSON-RPC waits.
  - Rework util.CraftPyExecutors (fixes P8): separate pools for (a) file
    IO/builds, (b) Python RPC, (c) background UI tasks; bounded queues
    with a policy that drops/coalesces stale work (hot reload spam);
    per-project and per-module SERIAL executors so one project never
    builds twice in parallel; every task wrapped so exceptions are
    always logged; lazy pool (re)creation so a second world in the same
    JVM works; cancellation tokens; a timeout fails the future AND sends
    a cancel to the worker.
  - Apply results to game state only on the correct main thread
    (server.execute(...) / Minecraft.getInstance().execute(...)); copy
    data into immutable snapshots before handing it to other threads.
  - Budgets: document and measure the per-tick overhead with N modules;
    expose it in the profiler.
